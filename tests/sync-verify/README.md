# stella-sync-verify — 두 기기 동기화 검증

> 저장소 위치: `tests/sync-verify/`. `lib/`는 `frontend/Frontend_UI/src/lib/stella/`의 모듈을 컴파일한 사본이에요. 서버 쪽은 `backend/supabase/`.

기기 A·B를 흉내 내서 **실제 Supabase 서버**에 대고 동기화를 확인합니다. 기기 DB는 진짜 SQLite 파일(`device-data/deviceA.db`, `deviceB.db`)이고, 동기화 코드는 앱 연결 모듈의 `local-sync.ts`와 같은 코드입니다(`lib/`는 그 파일을 컴파일한 것).

## 확인하는 것 (원격 115개 · 로컬 70개)

1. 로그인 → 내 프로필·설정 조회, 남의 설정은 안 보임(RLS)
2. A가 공간 생성 → B가 초대 코드로 참여 → 두 기기 처음 받기(스냅샷)
3. A 저장 → 보내기 → B 받기 → B SQLite에 데이터와 커서 저장 (앱을 다시 켜도 유지), 메모↔프로젝트 연결·해제
4. **끊김 후 재연결**: 끊긴 동안 저장한 2건이 연결되면 순서대로 전달, 여러 번 나눠 받기
5. **같은 요청 재전송**: 서버는 처리했는데 응답을 못 받은 경우 → 같은 operation_id로 다시 보내면 한 번만 저장
6. **두 기기 충돌**: 같은 메모를 둘이 고침 → 늦은 쪽 CONFLICT → "내 것 유지" / "서버 값 쓰기"
7. **전체 재동기화 때 안 보낸 수정 보존**: 서버가 전체 다시 받기를 요구해도 안 보낸 수정은 그대로, 그다음 전달
8. 휴지통에 간 기록을 다른 기기가 고친 경우
8-1. **메모 복구·손글씨·화면 칸 (11/15 추가, 5개)**: 프로젝트 진행 상태·마감·중요도, 일정 상태·알림, 공간 설명, 메모 손글씨가 다른 기기에 그대로 가는지 / 휴지통 메모 복구 → 다른 기기 목록에 다시 보임 / 두 기기가 동시에 복구하면 늦은 쪽은 서버 값 / 형식이 틀린 손글씨는 서버가 거절
9. 최종 일치: 두 기기의 메모 = 서버, 커서 = 서버 마지막 seq
10. **실시간 변경 신호 (원격만, 6개)**: B가 구독 → A 저장 → B가 신호 받음(Realtime 서버가 막 켜지는 중이면 첫 신호가 빠질 수 있어 최대 3번 저장해 보고, 몇 번째에 받았는지 결과에 남김), 신호로 자동 받기(`watchWorkspace`), 멤버 아닌 공간은 구독 거절, 공간 삭제 신호, 멤버도 가짜 신호는 못 보냄
11. **첨부 업로드·다운로드 (원격만, 11개)**: A 올리기 → 서버 확인 → B 받기·내려받기(내용 같음), 메모에 연결, 같은 id 재시도, 내용이 다른 파일 거절, 올리기 전 확인, 권한·형식·크기 제한, Storage 직접 업로드 차단, 삭제
11-1. **프로젝트 팀원·초대 (5개, 원격·로컬)**: A가 프로젝트를 만들면 A가 팀장으로 B 기기 목록에 → A의 링크 초대 코드로 B 참여(이미 공간 멤버라도 그 프로젝트 팀원으로) → **B가 자기 역할을 고치면 충돌(`NOT_PROJECT_LEADER`, 팀장만 관리, 11/15) → 서버 값 '팀원'으로 되돌림 → 팀장 A가 '디자이너'로 수정 → B 기기에 보임** → A가 팀장만 지우기는 막히고(LAST_LEADER) B를 다른 프로젝트로 이동 → 이번 달 초대 횟수
    - 한 번 돌릴 때마다 A의 이번 달 초대 횟수(FREE 10회)에서 1회를 써요. 다 쓰면 초대는 건너뛰고 팀원을 직접 추가해서 나머지를 확인해요
11-2. **메모 즐겨찾기 · 팀장 권한 · 프로젝트 파일 (원격 3개 · 로컬 2개, 11/15 추가)**: A가 메모 2개를 별표 → A 목록엔 있고 B 목록엔 없음, 하나 해제 반영 / A가 팀장인 프로젝트에서 팀원 B의 수정은 충돌로 되돌아가고 초대는 `FORBIDDEN`, 팀장 없는 프로젝트는 B도 수정, 서버 권한표 = 기기 계산 / (원격만) A가 올린 첨부를 B가 메모 없이 프로젝트에 연결 → A 기기에 보임 → A가 다른 프로젝트로 옮김 → B 기기에도 반영
11-3. **공유 휴지통 (3개, 원격·로컬, 11/15 추가)**: A가 할 일·메모를 휴지통으로 → B 기기 휴지통 목록에 둘 다(30일, B는 영구 삭제 버튼 없음) → B가 할 일 복구 → A 기기에서도 빠짐 → B의 메모 영구 삭제는 충돌(`PURGE_NOT_ALLOWED`) → 지운 A가 영구 삭제 → 두 기기에서 사라짐
12. 공간에서 내보내지면 그 기기에서 공간이 닫힘
13. **녹음 → 글자 (원격만, 7개)**: 노션 모바일처럼 녹음을 서버 임시 보관함에 올리고 → 변환 → **성공하면 서버가 바로 삭제**, **실패하면 3일 보관**해서 다시 올리지 않고 다시 변환. 20MB 녹음을 올려 서버가 OpenAI까지 보내는지(가짜 내용이라 거절되고 녹음은 남음), 2초짜리 시험음을 실제 `gpt-transcribe`로 변환하고 녹음이 지워지는지, 분 단위 사용량, 동의·공간·형식 거절, 보관함 직접 업로드 차단
    - 검증 계정 A에 외부 AI 동의를 자동으로 넣고, 한 번 돌릴 때마다 A의 녹음 변환 한도(월 60분)에서 **1분**을 써요(OpenAI 비용 약 $0.0045)
    - 실패 시험용 20MB 녹음은 하루에 하나만 남게 해 뒀고, 3일 뒤 자동으로 지워져요
14. **긴 녹음 (원격만, 5개)**: 최대 3시간 녹음 흐름. 녹음 등록 → 구간 2개(시험음) 업로드 → 서버가 파일·크기·소유자 확인 후 작업 등록 → 서버(`stt-worker`)가 앱 없이 구간별 전사(최대 90초 기다림) → 성공 구간 음성 즉시 삭제 → 전사문 받기·ack → 남의 경로·등록 안 된 경로 업로드 거절, 크기 다르면 등록 안 됨 → 취소
    - 한 번 돌릴 때마다 A의 녹음 변환 한도에서 **2분**을 써요. 서버에 OpenAI 키가 없으면 2·3번째가 실패하고 녹음은 자동 취소돼요
16. **가짜 결제 (계정 B, 7개, 원격·로컬)**: 구독 조회 → 결제 실패 시연(FREE 그대로) → PRO 선택(가짜 결제 1번, 같은 요청 재시도는 처음 결과) → **TEAM으로 바로 변경(9,900원, 초대 200회) → 다시 PRO(초대 50회)** (11/15 추가) → AI 한도가 PRO를 읽는지 → 무료 선택(해지 예약, 다음 결제일까지 PRO)
    - 원격 계정은 실행마다 상태가 남아요. 두 번째 실행부터는 B가 '해지 예약' 상태라 결제 실패 시연은 건너뛰고 PRO 선택은 결제 없이 해지 취소(RESUMED)로 확인해요. 한 달 뒤 B가 FREE로 돌아오면 다시 전체를 확인해요
15. **사진 → 글자 (원격만, 2개)**: "STELLA 2026"을 그린 시험 사진을 Terra가 실제로 읽는지, HEIC 같은 형식·6장 이상은 OpenAI에 보내기 전에 거절하는지. 한 번에 A의 사진 글자 한도(월 30회)에서 **1회**를 써요
    - 서버에 `OPENAI_API_KEY`가 없으면 이 묶음이 실패하고 결과에 "OPENAI_API_KEY 등록 필요"라고 나와요
15-1. **문서 → 글자 (원격만, 4개, 11/15 추가)**: Edge Function `doc-extract`. 기기 PDF(3쪽, 빈 쪽 표시) → Word(표·쪽 나눔)·PowerPoint(슬라이드·발표자 메모) → 공유 첨부로 올린 PDF를 A는 읽고 공간에서 빠진 B는 `ASSET_NOT_FOUND`(RLS) → 스캔본 `noText`·글 파일 `UNSUPPORTED_TYPE`. 외부 AI로 안 보내서 한도를 쓰지 않아요(올린 첨부는 끝나면 지움). 시험 파일은 `fixtures/docs/`
15-2. **AI 채팅·안건 판단 (원격만, 4개, 11/15 추가)**: ai-gateway `/query/plan`·`/query/answer`·`/agenda/judge`를 실제 Terra로. 질문 → 검색 조건 → 기기 기록(검증용 3개)에서 발췌 → 답변·출처(준비물 메모만 출처, 점심 메모는 아님) / 인사는 1단계에서 바로 답(기록 검색 없음) / 멤버 아닌 공간 기록이 섞이면 `FORBIDDEN`(OpenAI에 안 보냄) / 안건 비교: 회의에서 말한 변경은 논의됨(근거 구절이 회의 메모에 실제로 있음)·말 안 한 항목은 미논의, 같은 입력은 캐시
    - 한 번에 A의 이번 달 한도에서 질문 1회(FREE 50)·검색 조건 2회(FREE 150)·안건 판단 1회(FREE 50)를 써요. 모델 판단이라 아주 드물게 문구가 달라 실패할 수 있어요 → 결과의 답변·근거를 보고 판단해 주세요

## 준비 (처음 한 번)

1. **Node.js 22.13 이상** (권장: 24 LTS, https://nodejs.org). 내장 SQLite를 쓰기 때문이에요. `node -v`로 확인하세요.
2. **테스트 계정 2개**: Supabase 대시보드 → Authentication → Users → **Add user → Create new user**
   - 이메일과 비밀번호를 넣고 **Auto Confirm User를 체크**해요. 실제로 받을 수 있는 메일이 아니어도 돼요(예: `sync-a@stella.test`).
3. 이 폴더에서 패키지 설치:
   ```powershell
   npm install
   ```
4. `.env.example`을 복사해 `.env`를 만들고 계정 2개를 적어요:
   ```powershell
   copy .env.example .env
   notepad .env
   ```

## 가입·인증 메일 확인 (`auth-test.js`)

앱과 같은 방식으로 **이메일+비밀번호 가입 → 메일 6자리 코드 인증 → 로그인**, **비밀번호 재설정**을 실제 서버에서 확인해요. 메일을 받을 수 있는 주소를 써야 해요. 코드는 터미널에 직접 입력하고, `r`을 입력하면 다시 보내요.

```powershell
node auth-test.js signup 내메일+t1@gmail.com Stella2026! 테스트
node auth-test.js reset  내메일+t1@gmail.com Stella2027!
```

Gmail은 주소 뒤에 `+아무거나`를 붙여도 같은 메일함으로 와서, 테스트 계정을 여러 개 만들 수 있어요. 확인하는 것:
- 가입하면 인증 메일이 가고, 인증 전 로그인은 막힘
- 코드 자릿수, 코드 인증 후 로그인, 가입 트리거가 프로필 생성
- 이후 비밀번호 로그인, 틀린 비밀번호 거절
- 재설정 코드 → 새 비밀번호 저장 → 새 비밀번호로 로그인
18. **백업·복원 (원격만, 4개, 11/15 추가)**: 계정 A로 개인 기록 백업(기기에서 암호화, 서버 파일에 내용이 안 보이는지) → 목록 맨 위 → 같은 계정은 받아서 풀리고 B는 못 받음 → 복원(복원 전 상태가 "자동" 백업으로 남음) → 이번에 만든 백업 2개 삭제. 보관 개수는 50으로 둬서 예전 백업을 지우지 않아요
19. **알림 설정 · 알림함 · 탈퇴 미리 보기 (3개, 원격·로컬, 11/15 추가)**: B의 브리핑 설정을 화면 값('오전 7:30'·'금')으로 저장 → 07:30·5 → 다시 읽어 같음 (끝나면 원래대로) / 등록 안 된 기기 토큰은 `NOT_FOUND`, 알림함·읽음 / A의 탈퇴 미리 보기에서 검증 공간은 "삭제" (**실제 탈퇴는 하지 않음**)
20. **초대 메일 (원격만, 1개, 11/15 추가)**: A가 공간 초대를 만들어 **A 테스트 계정 주소로** 메일 → 10분 안 같은 주소는 `MAIL_TOO_SOON`. 서버에 `SMTP_PASSWORD`가 아직 없으면 `MAIL_NOT_CONFIGURED`(공유 문구로)도 통과. 만든 초대는 바로 취소

## 실행 후 서버에 남는 것

- 검증용 공간은 끝날 때 **삭제(휴지통)** 처리돼서 앱에는 안 보여요. 행은 DB에 남아요.
- 테스트 계정 2개는 그대로 남아요. 다음 검증 때 다시 쓰면 돼요.
- 매 실행마다 초대 1~2개(메일 확인용은 바로 취소), 메모·할 일 몇 개가 새 공간에 만들어져요. 휴지통 검증 메모는 영구 삭제돼요.

## 로컬 DB로 실행 (백엔드 담당용)

`supabase/tests`의 로컬 Postgres(`-p 54329 -k /tmp`)에 대고 같은 시나리오를 돌려요. 계정은 자동으로 만들어요.

```bash
npm run verify:local
VERIFY_FAKE_SNAPSHOT=1 npm run verify:local   # "전체 다시 받기"를 원격처럼 응답 흉내로
```

원격에서는 서버의 오래된 변경 정리 상태를 바꿀 수 없어서, 7번의 "전체 다시 받기"는 서버 응답을 흉내 내서 시작해요. 그 뒤 실제 스냅샷을 받아 반영하는 부분은 진짜 서버로 해요. 로컬 실행에서는 서버에서 커서를 실제로 무효화해서 확인해요.
