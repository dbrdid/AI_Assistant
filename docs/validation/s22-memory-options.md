# S22 가용 메모리 대응안

기록일: 2026-11-23. 이 파일은 커밋하지 않는다. **모델별 메모리 값은 GGUF 헤더와 llama.rn 소스에서 계산한 추정이며 S22 실측이 아니다.** M0은 첫 상태만 측정했고 M1~M3은 NOT_RUN이다. 앱 코드와 로드 조건은 바꾸지 않았다.

## M0 첫 측정 (2026-11-23 23:18경, 읽기 전용)

- 기기: SM-S901N, SM8450, Android 16, `BP2A.250605.031.A3.S901NKSS9GZH3`. 충전 중, 배터리 88%, 32.6°C. `dotprod`와 `i8mm` 지원.
- 상태: 다른 앱을 닫지 않은 평소 상태. 홈 화면이 전면이고 Stella는 실행 중이 아니다.
- `MemAvailable`: 2.36GiB(3회 측정 동일 수준).
- `dumpsys` Free RAM: 3.04GiB. 캐시 프로세스 0.84GiB와 커널 캐시 1.51GiB, 빈 메모리 0.70GiB의 합이다.
- ZRAM: 3.68GiB가 스왑되어 1.11GiB의 실제 메모리를 사용 중이다.
- 가중치와 `n_ctx` 1024 KV 합계 추정은 Q3 2.48GiB, IQ4_XS 2.57GiB, Q4 2.89GiB로 모두 `MemAvailable`을 넘고 Free RAM 안에는 든다. 계산 버퍼는 포함하지 않았다.

## M0 재측정 (2026-11-23 23:19경, 최근 앱 모두 닫은 뒤)

- `MemAvailable`: 2.31~2.48GiB(6회, 5초 간격). 3.0GiB 기준 미달이다.
- `dumpsys` Free RAM: 2.64GiB. 첫 측정 3.04GiB보다 낮다.
- 최근 앱을 닫아도 백그라운드 프로세스가 남거나 다시 떴다. 토스 0.58GiB, 인스타그램 0.24GiB, 카카오톡 0.18GiB 등이 측정 시점에 메모리를 사용했다.
- Free RAM 대비 여유 추정: Q3 0.16GiB, IQ4_XS 0.07GiB, Q4는 0.25GiB 부족. 계산 버퍼를 넣으면 여유가 더 줄어든다.
- 판정: 가중치 전체를 RAM에 유지한다는 전제로는 평소 사용 상태의 S22에서 4B 모델을 안정적으로 운용한다고 볼 수 없다. 부분 상주 시 속도는 M1로만 확인할 수 있다.

- 판정: IQ4_XS는 로드와 실행은 가능하지만 현재 프롬프트와 요청별 로드 방식으로는 S22 기준을 충족하지 못한다.

## 프롬프트 상태 저장 결과 (2026-11-24 00:05~00:30경, IQ4_XS)

조건: M1과 같은 측정 프로그램, 재배치 끔, 큰 코어 4개, 개발셋 d01~d05. **앱 경로가 아니며 승인·저장은 NOT_RUN이다.**

- 저장: 고정 프롬프트 400토큰 계산 47.7초, 파일 기록 0.26초, 파일 65.8MB. 같은 조건의 첫 시도는 150초 제한을 넘겼다.
- 복원: 0.13~0.23초. 같은 프로세스 재복원은 0.03~0.04초.
- 빠른 구간 첫 토큰: d01 3.3초, d03 4.2초, d02 5.9초.
- 느린 구간: d01 첫 토큰 15.7초·전체 95.3초, d04 첫 토큰 17.0초·전체 121.8초, d05는 150초 제한 초과. 전체 프롬프트 기준 실행도 d02·d03 모두 200초 제한을 넘겨 출력 동일성은 비교하지 못했다.
- 대기 중 10초 동안 스왑 인 5,209건, 주요 페이지 폴트 5,632건이 관측됐다. 스왑·페이지 재적재가 지연 원인일 가능성이 높지만 **원인은 미확정**이다.
- 출력: d01·d02·d04는 정답, d03은 값 없는 `문단 블록 추가`(검증기가 차단할 출력), d05는 미완료.
- 측정 프로그램 결함: 초기 연속 처리의 d02~d05 `지원불가`는 요청 간 상태 재사용 문제로 보고 결과에서 제외했다. 매 요청 복원으로 고쳤지만 연속 5건은 시간 제한으로 끝까지 확인하지 못했다.
- 판정: 저장·복원 자체는 동작하고 고정 프롬프트 계산을 없앤다. 그러나 IQ4_XS는 이 기기의 메모리 압박에서 지연 편차가 커 4초 기준을 안정적으로 충족한다고 볼 수 없다.

## 상태 파일 사전 배포안

모델 다운로드 때 상태 파일을 함께 받으면 기기의 첫 계산(약 48초)을 없앨 수 있다. 조건은 다음과 같다.

- 파일을 모델 SHA-256, 렌더링 프롬프트 해시, llama.rn 버전, `n_ctx`·`n_batch`·`n_ubatch`, CPU 라이브러리 종류에 묶는다.
- 다운로드 후 SHA-256을 검사하고, 복원 실패나 토큰 불일치 시 파일을 버리고 일반 계산으로 돌아간다.
- 다른 기기나 다른 CPU 라이브러리에서 복원되는지는 NOT_RUN이다.

## 다음 후보 (다운로드 전, 모델 카드 검색 수준)

1. **Qwen3.5-2B:** 같은 계열이고 공식 모델 카드가 Apache-2.0이다. 커뮤니티 GGUF 중 약 1.07GB 체크포인트가 있다. 앱 프롬프트와 템플릿을 가장 적게 바꾸고 비교할 수 있다.
2. **Raon-1 nano:** 한국어·영어, Apache-2.0, GGUF 제공으로 표시된다. 템플릿과 품질은 별도 확인이 필요하다.
3. **EXAONE 4.0 1.2B:** 공식 GGUF가 있으나 현재 라이선스 파일을 확인하기 전에는 채택하지 않는다.

## 현재 차단 원인

- 전달받은 S22 기록: 가용 메모리 1.97GB(1.83GiB), Q4 로드 기준 3.75GB.
- 기준은 `mobileModelPolicy.mjs:11`의 파일 크기 + 700MiB이다.
- 기준만 낮추는 것은 해결이 아니다. 추론은 매 토큰 거의 모든 층의 가중치를 읽으므로, mmap을 써도 가중치 대부분이 RAM에 있어야 속도가 유지된다.

- 재배치 범위의 폭은 Q8_0 텐서(0.24GiB)의 재배치 여부가 불확실하기 때문이다.
- KV 캐시 추정: `n_ctx` 4096은 330MiB, 2048은 165MiB, 1024는 83MiB. 계산 버퍼는 별도이며 측정이 필요하다.
- **결론: 가용 1.97GB 그대로면 Qwen3.5-4B의 세 양자화 모두 가중치 전체가 RAM에 들어가지 않는다.** 먼저 가용 메모리를 늘려야 한다.

## 대응안 (권장 순서)

1. **가용 메모리 확보 측정.** 최근 앱을 닫고 release 빌드에서 재측정한다. 디버그 빌드와 Metro 연결이 쓰는 메모리가 빠지는지 확인한다.
2. **재배치 끄기.** `initLlama`에 `no_extra_bufts: true`를 준다(`llama.rn/cpp/jsi/JSIParams.cpp:371`). 가중치가 파일 기반으로 남아 OS가 회수할 수 있어 강제 종료 위험이 줄어든다. 대신 추론이 느려질 수 있다.
3. **앱 명령용 `n_ctx` 축소.** 명령 프롬프트는 약 420토큰이므로 1024를 후보로 한다. 긴 입력은 별도 설정이 필요하다.
4. **IQ4_XS 우선 시험.** 파일이 Q4보다 0.32GiB 작고 재배치 메모리가 가장 적다. 앱 기본 모델 교체는 선별셋과 S22 측정 뒤에 결정한다.
5. **그래도 부족하면 더 작은 모델.** 1~2B급 모델은 새 다운로드와 품질 재평가가 필요해 별도 승인 대상이다.
