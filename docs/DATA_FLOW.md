# 데이터와 AI 요청 흐름

## 로컬 저장

입력 → 경계 검증 → 앱 서비스 → Repository → SQLite 커밋 → 화면 반영 흐름을 유지합니다. 파일 본문은 앱 전용 저장소에, 파일 참조와 메타데이터는 DB에 둡니다.

논리 데이터는 원문, 메모, 할 일, 일정, 정리 실행·초안·결과, 변경 버전입니다. 기존 P0의 organization_* 정리 경로를 유지합니다. 이 문서는 새 테이블·컬럼·DDL을 확정하지 않으며, 이후 프로젝트·기억·동기화 확장에는 별도 마이그레이션을 설계합니다.

## 새 입력 정리

1. 사용자가 원문을 입력하면 앱은 AI 응답과 무관하게 수동 저장 경로를 제공합니다.
2. AI 사용 시 보낼 내용·처리 위치를 표시하고 이번 요청 또는 명시한 범위의 전송 허용을 확인합니다. 외부 전송 금지 자료는 전송하지 않습니다.
3. 앱이 요청 식별자, 입력 revision, 과업, 허용 텍스트를 AI API Client에 전달합니다.
4. 서버가 인증·인가·입력 길이·요청량을 검사하고 모델을 호출합니다.
5. 서버가 구조화된 정리 초안과 업무 후보를 반환합니다.
6. 앱이 형식·날짜·원문 참조·최신성을 다시 확인하고 검토 화면에 표시합니다.
7. 승인 시점에 revision을 재검사하고 확정 데이터와 승인 결과를 같은 로컬 트랜잭션으로 저장합니다.

서버는 초안을 생성하며 모바일 정본을 직접 수정하지 않습니다. 승인 중복 탭과 응답 재수신으로 같은 항목이 중복 생성되지 않도록 기존 승인 영수증·멱등성 설계를 이어갑니다.

## 기록 질문

질문 → 서버의 조건 해석 → 앱의 허용 DTO 검증 → 로컬 검색 → 사용자가 허용한 근거 발췌 전송 → 서버 답변 → 실제 근거 ID 확인 → 출처 표시 순서입니다. 조건 해석에는 질문만 보내고 DB 전체를 보내지 않습니다. 모델 생성 SQL은 실행하지 않습니다.

앱은 접근 범위·삭제 상태·AI 제외 설정을 적용해 근거를 고릅니다. 결과가 없으면 근거 부족으로 안내하고, 존재하지 않는 ID나 범위 밖 기록을 인용한 결과는 반영하지 않습니다.

## 요청·응답 계약 초안

아래는 필드 역할을 설명하는 설계이며 확정 API나 구현 코드가 아닙니다. 실제 필드명·스키마·엔드포인트·오류 코드는 개발 착수 시 공동 확정합니다.

| 요청 | 의미 |
| --- | --- |
| 요청 ID / 과업 | 중복 추적, 정리·조건 해석·근거 답변 구분 |
| 입력 revision | 이후 편집으로 오래된 결과가 되는지 판정 |
| 텍스트 / 근거 목록 | 과업에 필요한 최소 내용과 실제 기록 ID·revision |
| 언어 / 시간대 / 기준 시각 | 날짜 해석과 출력 기준. 앱이 해석 결과를 검증 |

| 응답 | 의미 |
| --- | --- |
| 요청 ID / 입력 revision | 현재 요청과 대조 |
| 결과 초안 | 과업별 구조화된 정리·후보·답변 |
| 출처 참조 | 전달한 근거의 ID·revision 또는 원문 구간 |
| 오류 유형 | 인증 만료·입력 초과·요청 제한·일시 장애·형식 오류 구분 |

## 오류·개인정보

- 오프라인·타임아웃·서버 장애: 작성 내용과 저장된 기록을 유지하고 재시도 동작을 제공합니다.
- 취소·화면 이탈·입력 변경: 늦은 결과를 저장에 반영하지 않습니다.
- 인증 만료: AI 호출을 중단하고 재인증 상태를 표시합니다. 수동 저장은 유지합니다.
- 재시도: 자동 반복을 기본 도입하지 않습니다. 재시도 범위·횟수·중복 비용 방지는 서버 계약에서 확정합니다.
- 전송 동의는 동기화·백업·제3자 제공 동의를 대신하지 않습니다.
- 운영 목표는 요청 처리 후 원문을 지속 보관하지 않고 본문·토큰을 로그에 남기지 않는 것입니다. 메모리·프록시·런타임 로그와 공급자 정책까지 실제로 검증해야 합니다.
- 서버가 모바일 기록을 영구 보관하는 설계는 이번 변경에 포함하지 않습니다.
