# One-attempt durable AI worker

`createWorker(options)` returns `runOnce()`. It claims at most one durable SQL job; an empty queue returns `idle`. `createWorkerStore(rpc)` supplies named RPC mapping. All executor RPCs require the server-only `ai_executor` role (enforced by the role allowlist in `rpc/index.js`; see `AI-DATABASE.md`).

Required injected adapters:

- `loadInput(job)` must authorize and decrypt the opaque encrypted reference, return its exact UTF-8 text in memory, and never persist/log plaintext. The worker checks the SHA-256 against explicit consent.
- `saveDraft({job,draft,kind,source_revision})` must encrypt the result at rest and return an opaque reference. It creates a draft only, never mutates the original. A late stale fence may leave an unreferenced encrypted draft requiring lifecycle cleanup.
- Trusted routes use `{id,provider,model,retention_version,max_cost_microusd,max_output_tokens}`. IDs must agree with the immutable SQL registry and consent metadata; no caller-supplied endpoint/model is used.
- Trusted provider exposes `noRetries: true`, a synchronous conservative `maximumCostMicrousd({model,input,maxOutputTokens})` returning a decimal string, and `complete({model,input,maxOutputTokens,maxCostMicrousd,signal})`. It must genuinely disable SDK/HTTP retries, enforce token/cost limits and not independently make background calls. This interface declaration does not make a live provider billing guarantee. No production provider is included.

Provider response: `{draft:{summary,action_items:string[],citations:[{start,end,quote}]},cost_microusd,provider_event_id}`. Citation offsets are JavaScript UTF-16 string indices and exact quoted spans must match the input. Additional draft fields, invalid quotes, unbounded usage and non-opaque provider event IDs are rejected. Output is always untrusted draft content; rendered clients must escape it and require user review.

The worker loads and validates input/cost bounds before `ai_begin_dispatch`, whose transaction makes the final consent, revision, permission, cancellation and live-lease check. Only returned `dispatched` permits one provider call. Cancellation can race after this boundary; once dispatched it cannot guarantee prevention of submission/billing. Timeout, provider error, malformed result, storage or settlement uncertainty transitions to `outcome_unknown` and retains the hold. There is no automatic retry. This includes every failure after a provider response: malformed output, citation mismatch, storage failure and settlement errors all become `outcome_unknown` even when the response carried a valid cost and provider event ID, and settlement is not retried (finding high 8 of the 2026-11-09 backend review in `docs/implementation-status.md`; fix planned in P0-5). Stale fencing blocks settlement and reports reconciliation required. The timeout aborts a supporting adapter, but an adapter ignoring abort may finish later; that promise is never used to settle or retry.

Budget reconciliation is an explicit executor responsibility using verified provider evidence. Never infer zero cost from an exception. Lease recovery needs a scheduler that calls `ai_reap_jobs`, and none exists yet; until it runs, crashed jobs stay `claimed` or `dispatched` and count as active (the user can still cancel a `claimed` one). Reaped claimed jobs (crashes before dispatch) are requeued, not failed, with no attempt limit. Crashes after dispatch become `outcome_unknown` only once the reaper runs, and then occupy the actor's active admission slots until someone reconciles them manually; the only SQL exit is `ai_settle_job` with a provider event ID and a cost within the reservation. Input JavaScript strings cannot be securely zeroized; hardening process memory/logging and encrypted-storage lifecycle are deployment responsibilities.

Tests use synthetic data and injected mocks only. No real account, network provider, KMS or billing operation is executed.

## Failures before dispatch

`ai_begin_dispatch` and `ai_fail_before_dispatch` raise contract errors (`shared/contracts/errors.js`) inside their transaction, which then rolls back, so nothing was dispatched or released. When either RPC fails with an error whose SQLSTATE and message match a contract entry exactly, the run returns `{id, state: "not_dispatched", reason}`, for example `stale_fence` (another claim holds the job), `not_claimed` (the lease expired or the job is no longer claimed) or `job_not_found`. The provider is not called and the RPC changed nothing. After `stale_fence` or `not_claimed` the job keeps its state and hold; an expired claim returns to the queue only when `ai_reap_jobs` runs. `job_not_found` means the job no longer exists: since P0-3 a job is deleted together with its consent, its workspace and that workspace's budget rows (holds included) when the workspace's sole member deletes the account (`backend/AI-DATABASE.md`), so there is no job or hold left to reconcile. Any other failure, such as a transport error or a SQLSTATE outside the contract (for example `42501`), returns `{id, state: "reconciliation_required"}` because the transaction may have committed: after a lost `ai_begin_dispatch` response the job can be `dispatched` although the provider was never called. This worker state is unrelated to the SQL reason `not_dispatched`, which `ai_mark_unknown` and `ai_settle_job` raise. Failures after dispatch are handled as described above.

A job whose actor's account was deleted (`actor_id` NULL; its workspace still exists) also stops before dispatch. The bundled vault (`backend/adapters/encrypted-vault.js`) binds `actor_id` into each object's AES-GCM AAD and refuses a context whose `actor_id` is not a UUID before decrypting, so `loadInput` throws. The worker handles that like any other local check that fails before dispatch: it calls `ai_fail_before_dispatch`, the run returns `{id, state: "failed"}`, the workspace hold is released (the actor's budget row went with the account) and the provider is never called (`backend/tests/ai.integration.test.mjs`). An input adapter that did not need the actor would reach `ai_begin_dispatch` instead, which returns `cancelled` for such a job because a consent without an actor is never allowed. A job's workspace is deleted only when its sole member deletes the account. If that happens after `ai_begin_dispatch` returned `dispatched`, the cascade deletes the job together with its attempt row (and the workspace's budget rows with their holds), so a provider call that may have been billed has no SQL record left. `ai_settle_job` and `ai_mark_unknown` then answer `job_not_found` as well, and the run returns `reconciliation_required`, the same path as a stale fence at settlement (read from the code; the tests cover that path with `stale_fence`, not with a deletion). The encrypted draft saved before settlement stays unreferenced, and no RPC can record or reconcile that charge; this is left to the AI state-machine exits of P0-5.

Precondition: the executor RPC transport must make exactly one attempt per `ai_begin_dispatch` and `ai_fail_before_dispatch` call. A transport that retried internally could commit the first attempt, lose its response and then get `not_claimed` on the retry; the worker would report `not_dispatched` for a job that SQL already marked `dispatched`. A transport that retries must report that ambiguity as a non-contract error, so the run returns `reconciliation_required`. The bundled SQLite bridge (`adapters/sqlite-ai.js`) runs each call once.

## Late cancellation and storage cleanup

An optional `deleteDraft(ref)` adapter removes a newly saved encrypted draft when authoritative settlement returns any state other than `succeeded` (including late cancellation). Cost settlement is not retried or marked unknown because of cleanup failure. If cleanup is absent or fails, the run returns `{state: "cleanup_required", job_state: <settled state>}`; operators must reconcile unreferenced encrypted storage separately. A successful cleanup returns the settled job state. If settlement itself has an uncertain outcome, the worker does not delete the reference because the DB may have committed it; reconciliation must first check the authoritative result and then remove orphaned ciphertext. Missing key/storage lifecycle integration remains a deployment gap.

A successful result with `source_stale: true` is surfaced as a stale draft for explicit user review, never automatically applied. Cancellation after submission still settles verified actual cost but SQL suppresses the late result reference.
