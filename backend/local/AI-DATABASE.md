# AI consent and durable queue: local implementation

Migration `202611090002_ai.sql` follows the sync migration. This is local, synthetic-data-tested infrastructure, not a deployed AI service. No routes, real budgets, credentials, provider calls, KMS or production services are configured by this migration. Personal SQLite records remain plaintext and untouched. AI drafts never mutate documents.

## Trust and privileges

All six AI tables have RLS and no direct grants to `authenticated`, `anon`, or `ai_executor`. Functions are owned by the existing NOLOGIN, non-superuser, non-BYPASSRLS `sync_backend` table owner, with fixed `pg_catalog` search paths and explicit execution allowlists. New `ai_executor` is NOLOGIN, has no membership grants, and can only execute the listed privileged RPCs. A deployment must deliberately configure an authenticated gateway/worker identity. This migration grants nothing to `service_role`, but on hosted Supabase the default privileges of schema `public` grant EXECUTE on new functions to `service_role` and the migration does not revoke it, so `service_role` can call the executor RPCs until P0-4 (see `docs/implementation-status.md`). JWT verification and the production connection are outside the SQL implementation. Never expose privileged admission as a caller-controlled RPC or accept a client actor ID as verified identity. The account-deletion hook this migration replaces (`private.forget_user_hook`, see 'Account deletion') keeps its owner `sync_backend`, its pinned search path and no EXECUTE for any client role. A non-superuser migrator needed the privileges of `sync_backend` before P0-3 already: with a membership that has SET but not INHERIT, the sync migration fails in its ownership block (`permission denied for schema app` at `alter table app.workspaces owner to sync_backend` once schema `app` belongs to `sync_backend`), before and after P0-3, and this migration's own statements need USAGE and CREATE on schemas `app` and `private` and REFERENCES on the sync tables they point to. So INHERIT membership, or equivalent explicit grants, was required anyway. Replacing the hook adds one more reason: even with those explicit grants, a SET-only membership fails at the hook with `must be owner of function`. The `permission denied for schema app` failure point assumes that `sync_backend` may create in schema `public`. Where it may not, the sync migration fails earlier, at the first `alter function public.create_workspace(uuid,text) owner to sync_backend` (`permission denied for schema public`), with a SET-only membership and with SET and INHERIT alike, so `sync_backend` also needs CREATE on `public`. All of this was checked in PGlite, not on hosted Supabase; P0-4 has to settle it together with F47.

The route registry is immutable per route ID and unseeded. A new provider, model, retention policy or cap requires a new route ID. Registration is configuration, not permission to make paid calls. Consent explicitly records approved request metadata and requires the workspace's AI switch to be on, the user's current edit access to the document (`document_rank >= 2`) and the exact source revision (see 'AI switch and edit access'). Consent authorizes exactly one job, not standing or repeated spending: `consent_id` is unique in the jobs table. Purpose is currently limited to `summary`, and consent expiry must be in the future and no more than 24 hours from grant. Every parent folder ACL and workspace membership cap applies through `private.document_rank`. The worker must match its provider configuration to the returned immutable provider/model, verify the exact bytes against the approved SHA-256, and enforce a trusted total cost upper bound before dispatch.

Only opaque input/result references (`[A-Za-z0-9_-]{1,200}`) are stored, not URLs or payload bytes. References must point to an independently access-controlled store. SQL cannot verify what bytes a reference resolves to. Provider event IDs are opaque metadata, not secrets or response bodies.

## AI switch and edit access (F29 minimum)

Added in P0-3. The rest of F29 (governance, roles beyond this minimum) stays in P0-6.

- AI is off in every workspace until its owner calls `set_ai_enabled(w, true)` (sync migration, column `workspaces.ai_enabled`, default false; see `backend/README.md`). Switching does not bump `access_epoch`. The AI RPCs read the switch under the workspace lock.
- `ai_grant_consent`: after the request checks, the workspace lock and the route check (`invalid_route`), a caller who is not a member gets `invalid_consent`, the same answer for an existing and a missing workspace, before the switch is read, so a non-member cannot learn whether AI is on. A member gets `ai_disabled` while AI is off. Then `private.ai_allowed` decides (`invalid_consent`).
- `ai_admit_job`: after the workspace lock and the consent re-read, AI off is `ai_disabled`. This is checked before the replay path, so even an identical retry is refused, and nothing is reserved, while AI is off.
- `private.ai_allowed`, used by consent, admission and `ai_begin_dispatch`, returns false for a consent without an actor (its account was deleted) before anything else. Otherwise it requires the actor's current edit access to the document (`document_rank >= 2`, so every parent folder ACL and the workspace role cap apply), AI on in the workspace, a live document at the consent's source revision, and an unrevoked, unexpired consent. A viewer, or an editor whom a folder or document ACL limits to viewer, cannot consent; before P0-3 read access was enough.
- `ai_begin_dispatch` re-runs `ai_allowed` under the workspace lock, so a queued or claimed job is cancelled, releasing its holds, once AI is turned off, the actor is demoted or loses edit access through an ACL, the document changes or is deleted, or the actor's account is deleted.
- Unchanged: `ai_job_status` still returns draft references while the caller can read the document (`document_rank >= 1`).

## RPC contract

All functions return JSONB; PostgreSQL bigint amounts, revisions and fencing tokens are decimal strings in responses. `max_output_tokens` is a JSON integer. All amounts are integer microUSD. No floating-point accounting.

Authenticated caller RPCs:

- `ai_grant_consent(p_request jsonb)`: exact request keys `approved` (must be true), `provider_id`, `model_id`, `consent_id`, `workspace_id`, `document_id`, `source_revision`, `payload_sha256` (64 lowercase hex), `route_id`, `purpose`, `retention_version`, `max_cost_microusd`, `max_output_tokens`, `expires_at`. Field formats are validated before any cast (see Errors). Returns the normalized consent row with string revision/cost. Actor is always `auth.uid()`, never request input. Exact consent replay is allowed; changed reuse is rejected (`consent_id_reused`).
- `ai_revoke_consent(p_consent_id uuid)`: returns consent ID and revocation time. Also cancels queued/claimed jobs and flags dispatched/unknown jobs. A consent that disappears while the call waits for the workspace lock (its workspace was deleted with an account) is answered `forbidden`, as for no such consent.
- `ai_cancel_job(p_job_id uuid)`: owner-scoped; returns status. Queued/claimed reservations release exactly once. Dispatched/unknown retain reservations. A job that disappears while the call waits for the workspace lock is `job_not_found`.
- `ai_job_status(p_job_id uuid)`: caller must own the job. When document access has been removed, only ID, state and cancel flag are returned, without draft or input references.

Executor-only RPCs:

- `ai_set_route(p_request jsonb)`: exact keys `route_id`, `provider_id`, `model_id`, `retention_version`, `max_cost_microusd`, `max_output_tokens`. Immutable, idempotent configuration. No default routes.
- `ai_set_budget(p_workspace_id uuid,p_actor_id uuid,p_period text,p_limit_microusd bigint)`: actor NULL configures workspace account; a UUID configures that actor's workspace account, and the actor must be a workspace member (`actor_not_member`). Immutable limit per UTC `YYYY-MM`. Returns budget fields with string amounts. No default budgets.
- `ai_admit_job(p_actor_id uuid,p_request jsonb)`: exact request keys `job_id`, `consent_id`, `input_ref`, `payload_sha256`, `route_id`. Actor must come from independently verified gateway identity. Returns job. Request reuse is SHA-256 bound to all request fields and actor. Even an identical retry rechecks current consent, revocation, expiry, document revision and ACL before returning private references. Use the status endpoint for a revoked or expired job. A different job ID cannot reuse an existing consent (`consent_already_used`, decided before quotas). After the workspace lock the consent is read again: one that vanished meanwhile is `invalid_consent`, and AI switched off is `ai_disabled`, both before the replay path. Then it checks consent, route/hash, current edit access/revision, expiry/revocation, single use, quota and budgets in that order; reservation and queue insertion commit atomically.
- `ai_claim_job(p_lease_seconds integer default 60)`: lease must be 1–900 seconds; returns job or null. No worker identity is needed: monotonically increasing fencing token identifies claim authority.
- `ai_begin_dispatch(p_job_id uuid,p_fencing_token bigint)`: returns `dispatched` only after rechecking live consent, the AI switch, the actor's edit access, revision, expiry and cancellation, and that the job still has an actor. Otherwise returns `cancelled` and releases the hold. A stale fence, expired claim or previously dispatched job raises an error. Never call the provider if this RPC response is lost or state is not `dispatched`.
- `ai_fail_before_dispatch(p_job_id uuid,p_fencing_token bigint)`: valid, unexpired claimed jobs only; marks failed and releases reservation. Cannot release dispatched/unknown work.
- `ai_mark_unknown(p_job_id uuid,p_fencing_token bigint)`: dispatched/unknown only; retains reservation.
- `ai_settle_job(p_job_id uuid,p_fencing_token bigint,p_provider_event_id text,p_cost_microusd bigint,p_outcome text,p_result_ref text default null)`: dispatched/unknown only; outcome `succeeded` requires a result reference; `failed` requires NULL. Cost must be 0–reserved amount. Unique event and job ledger entries make identical settlement idempotent, changed settlement rejected (`settlement_conflict`), and prevent event reuse (`event_id_reused`). Both budgets spend the actual amount and release the entire hold atomically. If cancellation was requested after dispatch, usage still settles, but the job becomes `cancelled` with `result_ref` NULL. The private immutable ledger retains the provider outcome/reference for reconciliation or later cleanup; caller status never exposes that cancelled result.
- `ai_reap_jobs()`: returns `{reaped: number}`. Expired claimed jobs return to queued, receive a newer fence when claimed again; expired dispatched jobs become outcome_unknown. Unknown work never automatically requeues or releases holds. Nothing in this repository schedules it, and there is no attempt counter, so a job that repeatedly outlives its lease is requeued indefinitely.

Job responses include `id`, `workspace_id`, `actor_id`, `consent_id`, `input_ref`, `period`, `reserved_microusd`, `state`, `fencing_token`, `lease_until`, `cancel_requested`, `hold_released`, `created_at`, `result_ref`, plus `source_stale` (true when the source revision changed or document was deleted), and approved `document_id`, `source_revision`, `payload_sha256`, `provider_id`, `model_id`, `route_id`, `purpose`, `retention_version`, `max_cost_microusd`, `max_output_tokens`, and `expires_at`. The private request hash is never returned.

## Errors

Every business error follows the shared contract in `shared/contracts/errors.js`, which is the source of truth for reasons, statuses and kinds. A function raises the reason as the message with SQLSTATE `PT<status>`; PostgREST answers HTTP `<status>` with `{code: 'PT<status>', message: '<reason>'}`. Any other SQLSTATE that reaches a caller is a server fault or misconfiguration, never a business decision: `42501` now only means a missing privilege (for example `permission denied for function ...`), not a denial. Request fields are validated before any cast or table constraint, so malformed input returns a contract reason rather than a raw PostgreSQL error.

| Reason | Status | Kind | Raised by |
|---|---|---|---|
| `unauthenticated` | 401 | auth | `ai_grant_consent`, `ai_job_status`, `ai_cancel_job`, `ai_revoke_consent` without a JWT subject (checked before any lookup) |
| `forbidden` | 403 | access | `ai_job_status`, `ai_cancel_job`, `ai_revoke_consent`: no such job or consent for the caller (a job or consent whose actor was deleted has no caller); `ai_revoke_consent` also when the consent vanished while the call waited for the workspace lock |
| `invalid_consent` | 403 | access | `ai_grant_consent`, `ai_admit_job`: the caller is not a member (an existing or a missing workspace alike), no current edit access (`document_rank >= 2`), changed source revision, deleted document, revoked or expired consent, a consent of another actor, a consent that vanished while admission waited for the workspace lock, or a payload hash or route the consent did not approve |
| `ai_disabled` | 403 | access | `ai_grant_consent` (members only), `ai_admit_job` (identical retries included): the workspace's AI switch is off |
| `workspace_not_found` | 404 | not_found | `ai_set_budget` |
| `job_not_found` | 404 | not_found | `ai_begin_dispatch`, `ai_fail_before_dispatch`, `ai_mark_unknown`, `ai_settle_job`: no such job, before or after the workspace lock (a job goes with its workspace when an account deletion deletes it); `ai_cancel_job` when the job vanished while the call waited for the workspace lock |

Validated request formats:

- `ai_grant_consent`: `consent_id`, `workspace_id` and `document_id` are UUID strings (8-4-4-4-12 hex digits, either case). `source_revision` and `max_cost_microusd` are decimal strings of 1–18 digits without a leading zero; JSON numbers are rejected. `max_output_tokens` is a JSON integer from 1 to 1,000,000. `expires_at` is a string that PostgreSQL parses as `timestamptz`, at most 24 hours ahead. `purpose` is `"summary"`, `payload_sha256` a string of 64 lowercase hex digits, and `retention_version` a string of 1–200 characters. A failure is `invalid_request`. `provider_id`, `model_id` and `route_id` are matched against the registry instead (`invalid_route`).
- `ai_set_route`: field values are converted by the column types as before, so the numeric fields accept JSON numbers or numeric strings. A conversion failure, a missing field, text outside 1–200 characters, `max_cost_microusd` below 1 or `max_output_tokens` outside 1–1,000,000 is `invalid_route`.
- `ai_admit_job`: `job_id` and `consent_id` are UUID strings, `input_ref` a string matching `[A-Za-z0-9_-]{1,200}`, `payload_sha256` a string of 64 lowercase hex digits, `route_id` a string, and `p_actor_id` is not NULL. A failure is `invalid_request`; a well-formed hash or route that the consent did not approve is `invalid_consent`.
- `ai_set_budget`: workspace ID not NULL, period `YYYY-MM` with month 01–12, limit not NULL and at least 0; otherwise `invalid_request`.
- `ai_settle_job`: provider event ID of 1–200 characters and a result reference that is NULL or matches `[A-Za-z0-9_-]{1,200}`; otherwise `invalid_request`.

Changed in P0-1 (earlier SQLSTATE in parentheses):

- Business denials no longer use `42501`: `unauthenticated` is `PT401`; `forbidden` and `invalid_consent` are `PT403`. Reasons that were raised without an errcode (`P0001`) now carry their contract status.
- `ai_grant_consent`: an expiry more than 24 hours ahead is `invalid_request`, no longer `invalid_consent`. Malformed or missing fields are `invalid_request` instead of raw cast and constraint errors (`22P02`, `22003`, `22007`, `22008`, `22009`, `22023`, `23502`, `23514`), for example a purpose other than `summary` or a payload hash that is not 64 lowercase hex digits. A `source_revision` of `0` is now `invalid_request` rather than `invalid_consent`.
- `ai_set_route`: conversion and constraint failures (`22P02`, `22003`, `23502`, `23514`) are `invalid_route`.
- `ai_set_budget`: a non-member actor is `actor_not_member` (was an errcode-less `forbidden`); a missing workspace is `workspace_not_found` (was `23503`, or `forbidden` when an actor was given); a malformed period or a negative or NULL limit is `invalid_request` (`23514`, `23502`).
- `ai_admit_job`: a second job for a consent is `consent_already_used` (`23505`) and is decided before quotas; missing budget rows are `budget_not_configured` instead of `budget_exceeded`; malformed fields are `invalid_request` (`22P02`, `23502`, and `23514` for an `input_ref` that is not an opaque reference).
- `ai_settle_job`: an event ID settled for another job is `event_id_reused` (`23505`); a malformed event ID or result reference is `invalid_request` (`23502`, `23514`).
- The consent, job and ledger inserts also convert a unique violation from a concurrent duplicate that the explicit checks cannot see (for example the same ID used in two workspaces at once) into `consent_id_reused`, `consent_already_used` or `job_id_reused`, and `event_id_reused`. Each backstop checks the violated constraint's name; any other unique violation is re-raised unchanged as a server fault. These races cannot be reproduced in the single-session tests, so only the raise statements are checked there.
- A JWT subject that is not a UUID makes `auth.uid()` fail with `22P02` inside the function. That is a token-issuer misconfiguration and is not converted.

Changed in P0-3:

- New reason `ai_disabled` (`PT403`) from `ai_grant_consent` and `ai_admit_job` while the workspace's AI switch is off.
- `invalid_consent` now also covers a member without edit access: a viewer's consent used to be accepted. Existing consents of a member who lost edit access are refused at admission and cancelled at dispatch.
- Jobs and consents can now disappear: they cascade from the documents and the workspace that account deletion deletes with a sole-member workspace. Every re-read under the workspace lock that can now find nothing raises a contract error: `job_not_found` in the fenced executor RPCs and `ai_cancel_job`, `forbidden` in `ai_revoke_consent`, and `invalid_consent` in `ai_admit_job`. Without these guards `ai_begin_dispatch` returns SQL NULL and commits when its job vanishes in that window, which the worker cannot handle (reproduced on the code without the guards in a one-session simulation).

Not covered by the contract: typed RPC arguments (`uuid`, `bigint`, `integer`, `text`, `jsonb`) are converted before a function body runs, so a value that is not of the declared type (for example `'not-a-uuid'` for `p_job_id`, a non-numeric fencing token, invalid JSON text, or a NUL byte in text) still fails with PostgreSQL's `22P02`, `22003` or `22021`, which the contract treats as a server fault. The gateway and the worker send only values that convert; a direct PostgREST caller of the authenticated RPCs can still trigger this.

## Transaction and retry invariants

Mutations lock workspace before jobs and budget rows. Budget rows lock in scope order. Workspace locking matches synchronization and ACL mutations. Queue claims and reaping use SKIP LOCKED. Account deletion locks, in id order and before it changes any row, only the workspaces where the user is a member. In a workspace the user no longer belongs to, the AI cleanup below takes row locks without the workspace lock. No RPC adds a row of the user there (consent and admission need edit access, a budget row needs membership), reaping skips locked rows, and the cleanup changes each row once; the only key it changes is the actor, set to NULL, which needs no check, so no foreign key check key-shares a parent row there (a second UPDATE of a row the transaction already wrote would re-run the checks). A call that holds one of the user's job, consent or budget rows delays the cleanup until it commits. A call that updates one of the user's jobs twice in its transaction, first in `private.ai_release` and then in its final UPDATE, can form a cycle instead: the second UPDATE re-checks the actor foreign key and waits for the `auth.users` row being deleted, while the cleanup waits for the job row. Such calls are the cancel path of `ai_begin_dispatch`, `ai_fail_before_dispatch`, `ai_settle_job`, and the user's own `ai_cancel_job` or `ai_revoke_consent` that cancels a queued or claimed job; `ai_mark_unknown` and the other paths change the job once. It can form in a workspace the user left as in one the user still belongs to (there the deletion waits for the workspace lock instead of the job row), so leaving first does not avoid it. In a workspace where the user is a member, a call that holds the workspace lock and inserts a row naming the user (an admission or a consent of that user, for example) waits for that `auth.users` row as well, while the deletion waits for the workspace lock (`backend/README.md`, '계정 삭제'). Another account deletion can form a cycle too: when it deletes a sole-member workspace in which the user still has AI rows (typically left there after the user left), its document cascade takes those rows before that workspace's invitations, receipts, signal rows and audit, while this deletion changes the user's invitations, signal rows, receipts, journal and audit rows first and reaches the AI rows last, in the hook (the other rows such deletions meet are in `backend/README.md`). The trigger's 250 ms lock_timeout bounds any such wait: a lock not granted within 250 ms, as in a cycle, fails the deletion with `55P03` for the caller to retry. The re-verification showed each direction of the executor wait separately in PGlite, with a prepared transaction holding the other side's locks, and the user's own `ai_cancel_job` of a queued or claimed job and `ai_revoke_consent` with a queued job waiting for the held `auth.users` row; the cycle itself and the lock_timeout cannot run in single-session PGlite, and the rest (the AI rows of two concurrent deletions included) is reasoned from the code, not run with real concurrent sessions. Each job reserves the full consent cap against BOTH actor-workspace and workspace budgets. Its period is fixed at admission, so settlement after month rollover uses the original period.

Admission permits at most 10 new jobs during the prior rolling minute and 3 active jobs per actor/workspace. Active includes queued, claimed, dispatched and unknown. Unknown jobs count with no time bound, and there is no reconciliation RPC: the only exit from `outcome_unknown` is `ai_settle_job` with a provider event ID and a cost within the reservation. Three unknown jobs therefore block that actor's admissions in that workspace indefinitely. Idempotent retries are checked before quotas/reservation. These deliberately conservative constants are code-level limits, not a production-configured distributed API rate limiter; request ingress also needs deployment limits.

There is one durable provider attempt per job and no automatic paid fallback. A timeout or crash after the dispatch marker may represent a billed request; the hold remains until trusted reconciliation settles it. Cancellation after dispatch does not claim to undo the provider request. If actual provider charges exceed the reserved cap, settlement fails closed (`invalid_cost`) and the hold remains. There is no RPC for operator reconciliation, and no RPC can record a provider charge above the reservation. This must not be represented as enforcing a provider's bill; the worker must establish a real provider cost upper bound before sending.

## Account deletion (F24)

Deleting an account hard-deletes its `auth.users` row, and the sync migration's `forget_user` trigger cleans up in the same transaction (`backend/README.md`, section '계정 삭제'). This migration plugs into it by replacing the no-op hook `private.forget_user_hook(u)` with `create or replace`:

- `private.forget_user_hook(u)` runs after the sync cleanup, so u's sole-member workspaces are already gone together with their AI rows. The trigger takes no workspace lock for the AI rows: in a workspace where u was a member it already holds the lock, and elsewhere the hook works row by row (see 'Transaction and retry invariants'). It sets `actor_id` to NULL on u's consents, one row at a time in id order. It does the same on u's jobs and, in the same UPDATE, replaces `request_hash` with `sha256(uuid_send(job id))`: the old hash covered the actor ID, so a candidate ID could have been confirmed against it, and replay needs no hash any more because admission looks consents up by actor. Last it deletes u's budget rows; until the jobs lost their actor, their `actor_scope` referenced those rows.

Schema support:

- `ai_consents.actor_id` and `ai_jobs.actor_id` are nullable. Their foreign keys to `auth.users` stay NO ACTION, so a reference the cleanup misses fails the whole deletion. Partial indexes `ai_consents_actor` and `ai_jobs_actor` serve the cleanup and the foreign key checks. `ai_consents_document` (workspace_id, document_id) serves the cascade from each document of a deleted sole-member workspace. `ai_jobs_actor_budget` (workspace_id, actor_scope, period) and `ai_jobs_workspace_budget` (workspace_id, workspace_scope, period), the exact columns of the two budget foreign keys, serve their checks when a budget row is deleted (account deletion, or the cascade from a deleted workspace): a check reads only the jobs that reference that row, so deleting a member's budget row of the same month as other actors' jobs reads none of them. They replace a single `ai_jobs_budget` (workspace_id, period), with which deleting such a row read every job of that month twice (2,000 job rows for 1,000 jobs, measured in PGlite). In exchange every inserted job and every job state change (not a HOT update, since `state` is in the `ai_queue` predicate) writes an entry into each of them, one index entry more than with `ai_jobs_budget`: 200 job lifecycles through the RPCs (consent, admission, claim, dispatch, settlement) wrote about 9.8% more WAL than with it, measured in PGlite. `ai_budgets` has no index that starts with `scope` (its primary key starts with `workspace_id`), so the hook's delete of u's budget rows scans the budget table (F61, still open).
- ON DELETE CASCADE from consents to documents, from jobs to consents, from attempts and the usage ledger to jobs, and from budgets to workspaces. Only `private.delete_workspace` deletes documents or workspaces, when account deletion removes a sole-member workspace, so its AI rows go with it: the usage ledger rows of its settled jobs, and also a job that is `dispatched` at that moment, together with its attempt row. A provider call that may have been billed then has no SQL record, and the worker's `ai_settle_job` and `ai_mark_unknown` get `job_not_found`, so the run returns `reconciliation_required` (`backend/worker/README.md`). This is reasoned from the code, not tested, and left to P0-5 (AI state-machine exits). A document purged from the trash keeps its AI rows, because the purge clears content without deleting the row.

Effects on work whose actor is NULL:

- `private.ai_allowed` returns false first, so `ai_begin_dispatch` cancels such a queued or claimed job. `ai_release` and `ai_settle_job` match the budget scopes `('', actor_id::text)`, which for a NULL actor is the workspace row only: cancelling releases only the workspace hold, and a dispatched job still settles, charging only the workspace budget. The NULL check comes first because `set_config(..., NULL)` stores an empty string, and the hosted `auth.uid()` would then fall back to the JWT claims of whatever session runs the executor.
- With the bundled worker such a job stops earlier: the vault cannot rebuild the input's binding without an actor, so the worker calls `ai_fail_before_dispatch` (state `failed`, workspace hold released) and never calls the provider.
- An `outcome_unknown` job keeps its workspace hold until it is settled, and nobody can cancel it, since cancellation is scoped to the actor.
- The deleted account's still-valid token reaches nothing: `forbidden` from `ai_job_status`, `ai_cancel_job` and `ai_revoke_consent`, `invalid_consent` from `ai_grant_consent`, and its unused consents admit no job.

What the cleanup does not reach. The actor is unlinked in the app tables; that is not anonymisation of every copy:

- Vault objects. Encrypted inputs and drafts stay in the vault; nothing deletes them (F44). Their AES-GCM AAD binds `actor_id`, so whoever holds the vault key can confirm a candidate actor ID by trying to decrypt.
- `ai_consents.payload_sha256`, an unsalted SHA-256 of the plaintext input (F65), and the other request fields stay.
- Supabase Auth's own tables and logs (not checked in this repository), and backups, WAL and PITR copies.
